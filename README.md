# SupportDesk Live — starter project

A mobile-friendly customer support starter built with HTML/CSS/JavaScript and Supabase. Customers use guest chat (name + email); staff use authenticated accounts. The included FAQ assistant is rule-based.

## Current status and important limitations

- The frontend can run in demo mode without credentials.
- Live chat requires a Supabase project and the SQL setup below.
- Enable **Anonymous Sign-ins** in Supabase Authentication for guest sessions.
- Staff accounts must be created by an administrator. Insert matching rows in `staff_profiles` using the Auth user's UUID.
- This is a starter implementation, not yet a production-certified 24/7 service.
- The sample self-assignment RPC is a basic demonstration. Before production, implement transactional capacity-aware routing, manual reassignment for supervisors/admins, presence heartbeat, queue limits, rate limiting, spam controls, and audited role administration in trusted backend functions.
- Test every RLS policy with separate guest, CSR, supervisor, and admin accounts before inviting customers.
- Supabase free-tier quotas and inactivity/pause policies can change. 500 simultaneous users are not guaranteed on a free plan.

## 1. Create Supabase project

1. Create a Supabase project on the free plan.
2. In Authentication → Providers, enable Email for staff.
3. In Authentication settings, enable Anonymous Sign-ins for guest chat.
4. Open SQL Editor and run `supabase/schema.sql`.
5. Copy Project URL and the publishable/anon key from Project Settings → API.
6. Open `app.js` and set `SUPABASE_URL` and `SUPABASE_ANON_KEY`.
   - These are public browser values. Never put a `service_role` key in frontend code.

## 2. Create the first staff user

1. In Supabase Authentication → Users, create an email/password user.
2. Copy that user's UUID.
3. In SQL Editor, insert a staff profile (replace values):

```sql
insert into public.staff_profiles(user_id, display_name, role, active)
values ('AUTH_USER_UUID', 'Support Admin', 'admin', true);
```

Create further staff accounts with role `csr` or `supervisor`. Keep admin privileges limited.

## 3. Add FAQ entries

```sql
insert into public.faq_entries(question, answer, keywords)
values
('Support hours', 'Automated support is available anytime. Human replies depend on agent availability.', array['hours','open','available']),
('Billing help', 'Tell us the date and a short description. Never send full card details.', array['billing','payment','refund']);
```

The frontend currently displays rule-based FAQ replies. For durable, server-generated bot messages and escalation, add a trusted Supabase Edge Function; do not let the browser impersonate a bot sender.

## 4. Run locally

You can open `index.html` directly for the visual demo. For a local web server, use any static server or the Cloudflare Pages local workflow. No build step is required for this plain HTML starter.

## 5. Deploy to Cloudflare Pages (manual, only when ready)

1. Put this folder in a Git repository.
2. Create a Cloudflare Pages project connected to that repository.
3. Framework preset: **None**.
4. Build command: leave blank.
5. Build output directory: `/` (repository root).
6. Deploy only after reviewing the security checklist below.

## 6. Optional Cloudinary attachments

Cloudinary is not required for text chat. For production uploads, prefer a signed upload generated by a trusted backend function. An unsigned preset can be abused if exposed; restrict allowed formats, file size, transformations, and upload preset permissions. Never upload private documents without considering access controls and retention.

## Production security checklist

- Replace demo FAQ logic with trusted backend automation if bot replies must be stored.
- Implement transactional automatic assignment with agent status and max concurrency.
- Implement supervisor/admin manual assignment and transfer with audit records.
- Restrict CSR visibility to assigned and queued conversations; supervisors/admins can review all conversations.
- Guest message SELECT policy permits only public messages. Internal notes are restricted to authorized staff.
- Add rate limits, abuse prevention, email validation, CAPTCHA/Turnstile, and message length limits.
- Add data retention/deletion policy and privacy notice compliant with applicable privacy law.
- Enable MFA for admin accounts.
- Configure backups and monitor database, bandwidth, Realtime connections and function invocations.
- Do not promise 24/7 human response unless shifts are staffed.

## Suggested next build steps

1. Harden RLS for internal notes and staff assignment scope.
2. Build server-side automatic/manual routing with capacity checks.
3. Add staff presence and supervisor dashboard.
4. Add secure Cloudinary upload flow.
5. Load-test with realistic concurrent connections.


## Android PWA and staff push notifications

This build adds an installable PWA shell and Android Chrome Web Push support. It does not replace the existing chat or its RPC functions.

### Included changes
- `manifest.webmanifest`, `sw.js`, and a 192px app icon.
- An administrator-only **Enable notifications** button in the inbox.
- Staff device subscriptions stored in `public.staff_push_subscriptions` with RLS.
- Supabase Edge Function source at `supabase/functions/supportdesk-push/index.ts`.
- VAPID public/private keys are stored in Supabase Vault. The private key is not included in this ZIP or browser code.

### Remaining dashboard configuration
The Supabase database and Edge Function are already prepared. To connect new customer messages to the function:

1. Open Supabase Dashboard → **Database** → **Webhooks**.
2. Create a webhook named `supportdesk-customer-message-push`.
3. Table: `public.messages`; event: **INSERT**.
4. Webhook destination: **Supabase Edge Function** → `supportdesk-push`; method **POST**.
5. Add the authorization header using the dashboard's **Add auth header with service key** option. Keep JWT verification enabled.
6. Create/save the webhook.

The Edge Function ignores all inserts except public customer messages. It notifies the assigned active staff member; if the conversation is unassigned, it notifies active administrators and supervisors. Notification text is generic and does not reveal the customer's message on the lock screen.

### Publish the website
Deploy the contents of this folder to the existing Cloudflare Pages project (`support-desk-live.pages.dev`). Keep the site on HTTPS.

### Enable on Android
1. Open the website in updated Chrome.
2. Sign in using the administrator account.
3. Tap **Enable notifications** and allow Chrome notifications.
4. Optional: Chrome menu → **Add to Home screen** / **Install app**.
5. Send a test message from a separate customer browser/device.

### Important
- Push requires internet access and Android/Chrome notification permission.
- Android battery optimization or vendor background restrictions can delay delivery.
- The offline cache covers the app shell only; chat and Supabase data still require internet.
- Do not put a Supabase service-role key or VAPID private key in frontend files.


### Customer identity in Android push notifications

The push Edge Function now looks up `guest_profiles.full_name` using the message `sender_id`. Android notifications display:
- Title: `New message from [customer name]`
- Body: a short preview of the customer's message (up to 120 characters)
- Notification tag: conversation-specific, so different conversations remain distinguishable
- Tap action: opens the staff dashboard (`/#agent`)

If the customer profile has no name, the title falls back to `New message from A customer`. The database webhook must invoke the deployed `supportdesk-push` function for INSERTs into `public.messages`. Redeploy the Edge Function after updating it. This is a Progressive Web App (PWA), not a native APK; Chrome's Install app option depends on Chrome's installability checks.


## Combined update: admin session restore + sender-aware push alerts

This package combines the administrator session persistence fix and sender-aware push notification update in the same codebase. Deploy all files together; do not mix individual files from older ZIPs.

### Admin session behavior
- Supabase Auth persists sessions in local storage and refreshes tokens automatically.
- When opening `/#agent`, the app checks the saved session and validates that the user is still an active administrator before restoring the inbox.
- The Sign out action still ends the session.
- Clearing site data, using Incognito, revoking a session, or disabling the staff account will require signing in again.

### Notification troubleshooting
A browser message saying "Notifications enabled" means the browser permission and device subscription were saved. It does **not** prove the server has sent a push. Actual alerts also require:
1. Both migrations in `supabase/migrations/` applied to the correct project.
2. VAPID public/private keys stored in Supabase Vault; the public key in `app.js` must match the Vault public key exactly.
3. `supportdesk-push` Edge Function deployed to the same Supabase project, with the service-role secret available only to the function runtime.
4. A Database Webhook on `public.messages` for INSERT events, invoking the deployed function with the required authorization.
5. A customer message inserted by the `guest_send_message` RPC with `sender_role = customer` and `visibility = public`.
6. A valid staff subscription for an active admin/supervisor or assigned active agent.

The function resolves the sender's display name from `guest_profiles.full_name` using the inserted message's `sender_id`, and sends a short message preview. If the function or webhook is not deployed/configured, no Android notification will arrive even though browser permission is allowed.

### Android checks
- Android Settings → Apps → Chrome (or installed SupportDesk app) → Notifications: allow notifications.
- Android Settings → Apps → Chrome → Battery: allow background activity / unrestricted battery if the device provides that option.
- Turn off Data Saver restrictions for Chrome if enabled.
- Keep the phone connected to the internet for delivery.
- Re-enable notifications from the admin page after deploying if the site data or service worker was cleared.

3. Deploy the `supportdesk-push` Edge Function and keep JWT verification enabled.

6. Send a customer test message and inspect the Edge Function logs and webhook delivery result.

The website must be deployed over HTTPS. Android notification permission alone does not prove that server-side push delivery is configured. Do not expose the Supabase service-role key or VAPID private key in frontend files.
